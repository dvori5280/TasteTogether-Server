# TasteTogether

## תיאור המערכת

TasteTogether היא מערכת ניהול סדנאות בישול ומתכונים. מנהלת (Admin) יוצרת מתכונים וסדנאות, מפרסמת סדנאות ומקשרת מתכונים אליהן. משתמשות רגילות (User) מדפדפות במתכונים ובסדנאות שפורסמו, נרשמות לסדנה ומבטלות הרשמה כל עוד הסדנה לא התחילה. השרת הוא ASP.NET Core 8 Web API עם EF Core ו-PostgreSQL, אימות באמצעות JWT, AutoMapper, לוגים עם NLog ובדיקות xUnit ו-Moq.

## המשאב המוגבל והתחרות עליו

**המשאב המוגבל** הוא מקומות בסדנה: לכל סדנה יש `Capacity`, ומספר ההרשמות אינו יכול לעבור אותו.

**התחרות** מתרחשת כשכמה משתמשות מנסות להירשם בו זמנית למקום האחרון. אם הבדיקה "יש מקום?" והשמירה אינן מוגנות, שתיהן יעברו את הבדיקה ושתיהן יירשמו.

**הטיפול (Optimistic Concurrency):**
- לכל סדנה יש שדה `Version` (Guid) שמוגדר ב-EF Core כ-Concurrency Token. הוא מוחזר ללקוח בכל תשובה על סדנה.
- בקשת הרשמה חייבת לשלוח את ה-`Version` שהלקוחה ראתה.
- בעת הרשמה, ההרשמה וההחלפה של ה-`Version` נשמרות יחד ב-`SaveChanges` אחד. ה-UPDATE נוסח עם `WHERE Version = <הערך שנקרא>`.
- אם מישהי הספיקה להירשם קודם, ה-`Version` במסד כבר שונה, ה-UPDATE לא משפיע על אף שורה ו-EF זורק `DbUpdateConcurrencyException`. השירות מתרגם אותה ל-**409 Conflict** עם הודעה ברורה. שליחת `Version` ישן מחזירה אף היא 409.
- סדנה מלאה מחזירה 409 "הסדנה מלאה", והרשמה כפולה של אותה משתמשת נחסמת ב-409 על ידי אינדקס ייחודי על (UserId, WorkshopId).
- ההוכחה: בדיקה על PostgreSQL אמיתי עם שני `DbContext` נפרדים, ובדיקת Task.WhenAll שמריצה שתי הרשמות מקבילות על מקום אחרון. רק אחת מצליחה, והשנייה מקבלת 409.

## הוראות הרצה מקומית

**דרישות:** .NET 8 SDK ו-PostgreSQL מותקן מקומית (פורט 5432).

**1. הגדרת סודות (User Secrets).** הסיסמאות והמפתחות אינם נשמרים בקוד. מתוך תיקיית `TasteTogether.API`:

```
dotnet user-secrets set "ConnectionStrings:Default" "Host=localhost;Port=5432;Database=TasteTogetherDb;Username=postgres;Password=<הסיסמה שלך>"
dotnet user-secrets set "Jwt:Key" "<מחרוזת אקראית ארוכה, לפחות 32 תווים>"
```

**2. הפעלה:**

```
cd TasteTogether.API
dotnet run
```

במצב Development (ברירת המחדל של `launchSettings`), האפליקציה יוצרת את המסד אם הוא לא קיים, מריצה את ה-Migrations ויוצרת נתוני דמו. אין צורך בפעולה ידנית במסד. Swagger זמין ב-`https://localhost:7017/swagger` (או `http://localhost:5102/swagger`).

**3. בדיקות:**

```
dotnet user-secrets set "ConnectionStrings:Tests" "Host=localhost;Port=5432;Database=tastetogether_tests;Username=postgres;Password=<הסיסמה שלך>" --project TasteTogether.Tests
dotnet test
```

בדיקות המקביליות רצות על מסד נפרד (`tastetogether_tests`). הקוד מסרב לרוץ אם שם המסד אינו מכיל את המילה "test", כדי לא למחוק בטעות נתוני פיתוח. כרגע יש 148 בדיקות: שירותים עם Moq, Validation, הרשאות, Middleware, AutoMapper ותחרות על PostgreSQL אמיתי.

## משתמשי דמו (נוצרים אוטומטית בהרצה ראשונה)

- **Admin:** `admin@tt.com` / `Admin123!`
- **User:** `user1@tt.com` / `User123!`
- **User:** `user2@tt.com` / `User123!`

נתוני הדמו כוללים גם 2 מתכונים, סדנה מפורסמת עם 2 מקומות בלבד (`Challah Class`, מתאימה להדגמת 409) וסדנה בטיוטה (`Pasta Class`, גלויה ל-Admin בלבד).

## הרשאות ו-API בקצרה

- **פתוח לכולן:** התחברות והרשמה (`api/Auth`), רשימת מתכונים עם חיפוש, מיון ו-pagination, רשימת סדנאות שפורסמו.
- **משתמשת מחוברת:** הרשמה לסדנה וביטולה (`api/workshops/{id}/registrations`), וההרשמות שלי (`api/registrations/me`).
- **Admin בלבד:** יצירה ועדכון של מתכונים וסדנאות, שינוי סטטוס סדנה (טיוטה, מפורסמת, מבוטלת), קישור מתכון לסדנה, צפייה בנרשמות לסדנה וצפייה בסדנאות בטיוטה.
- קודי סטטוס: 400 קלט לא תקין, 401 לא מחוברת, 403 אין הרשאה, 404 לא נמצא, 409 תחרות או כפילות. פירוט מלא ב-Swagger.

## לוגים

NLog כותב לקונסול ולקובץ `logs/app-<תאריך>.log` (בתיקיית ההרצה). בכל בקשה יש `CorrelationId` שמופיע בכל שורות הלוג שלה וגם בכותרת `X-Correlation-Id` של התשובה. לא נרשמים סיסמאות, tokens או שאילתות SQL. רמת הלוג נקבעת ב-`nlog.config` ולא ב-`appsettings.json`.
